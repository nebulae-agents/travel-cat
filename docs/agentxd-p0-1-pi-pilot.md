# AgentX P0-1 · 一个 Pi 应用的双客户端运行

## M1 首段的多应用配置

同一私有根里的一个 agentxd 可以接管多个显式登记的应用运行目录。桌面和 CLI 按应用 ID 使用同一套[运行接口](../api/agentxd.openapi.json)。桌面可更新已读标记及发起或停止运行，这些请求由服务实际写入。服务停机后，配置标记仍约束桌面的写入。

在临时验收根里先准备应用定义及各自的 `apps/<appID>/runs/`。新版 `.agentxd-pilot.json` 支持如下形态。

```json
{
  "root": "/absolute/private/test-root",
  "version": 2,
  "apps": [
    {"appID": "test-alpha"},
    {"appID": "test-beta"}
  ]
}
```

每个应用可配置自己的 `pi` 绑定。无绑定时仍可读取或修改既有运行的已读标记。根路径填写解析后的绝对路径，配置文件总大小最多 2 MiB。桌面沿用原有的全根运行 ID 唯一规则，启用前请确认纳入的历史记录符合该规则。服务和 CLI 的接口则按应用 ID 与运行 ID 定位记录。已有单应用配置继续使用顶层 `appID` 和可选的 `pi`。操作者应在桌面和服务都退出后变更所有权标记，并用支持对应配置的桌面与服务版本验证后再启动。本段以隔离副本验证运行目录，配置文件、实例和发布内容后续逐级移交。

下文保留原单应用试点及历次验收记录。

2026-11-12。本文是基于 [build 58 实现](agentx-build58-architecture-and-interactions.md) 的试点设计。第 2 节是完整试点的目标契约，第 4 节记录单写者验收，第 5 节记录真实 Pi 的双端运行和重启回读，第 6 节记录正常停止后的独立复跑与正式数据比对，第 7 节记录退出凭据写入前服务中断的恢复验收。

首个交付场景为桌面发起一次 Pi 运行，CLI 读取并请求停止，桌面收到同一运行的退出确认。两个客户端与守护进程分别重启后仍能回读同一终态。试点使用现有数据的隔离副本，沿用文件存储。

## 1. 当前写入者与试点归属

| 当前入口 | 实际写入或副作用 | 试点处理 |
| --- | --- | --- |
| [桌面 Controller](../Sources/TravelCatApp/AgentXController.swift) · send、cancel、commit | 创建运行、消费回复、记录停止请求，经 Repository 保存状态 | 试点 Pi 运行的创建、取消和终态提交全部交给 agentxd；桌面用同一接口读取 |
| [Repository.save](../Sources/TravelCatApp/AgentXRepository.swift) | 遍历内存 run 列表，跳过语义相同的文件；用根级事务日志保护多文件保存 | 给旧桌面保存入口加所有权边界。桌面持有旧状态时，即使只是保存导航，也可能把服务刚写的 run 判为不同并写回。试点由守护进程单独写 run 文件与独立事务，避免共享根级回滚日志 |

| [运行审计](../Sources/TravelCatApp/AgentXRunAudit.swift) | 为开始、请求取消及完成追加审计事件 | 试点从服务端产生审计，关联同一 run ID；桌面订阅结果 |
| [停止操作存储](../Sources/TravelCatApp/AgentXStopOperation.swift)、[应用包事务](../Sources/TravelCatApp/AgentXApplicationLifecycle.swift) | 应用级停止意图、操作归档、安装/卸载/恢复涉及整个应用目录 | 首轮允许按 run 停止；试点应用的停用、卸载、恢复及整根迁移在所有权交接前须能拒绝或协调，避免与活跃服务并写 |
| [旅行 CLI](../Sources/TravelCatCLI/main.swift) 与后台旅行调度 | claim、publish、明信片处理可更新旅行域 | 旅行域维持现有写入路径。新增 agentx CLI 只通过服务操作试点 Pi run |

**第一道验收是写权限归属。** 服务按隔离根目录取得排他锁，再开放接口；第二个服务启动应明确报根目录已占用。试点归属在首次启动前随配置确定，服务掉线时桌面显示不可用，恢复连接后重新读取。旧版应用不认识这项归属，因此初期只用隔离根。

## 2. 最小接口契约（拟议 v1）

本机监听 loopback，桌面与 CLI 使用同一访问令牌，令牌由当前用户私有配置提供。服务端固定数据根并校验 app 与 instance 归属；命令参数不接受数据文件路径或模型密钥。

| 方法与路径 | 输入与返回 |
| --- | --- |
| POST /v1/apps/{app}/runs | 输入 instanceId、prompt 与 Idempotency-Key；先持久化命令及 runId，再返回 201 与 run 快照。同一键同一输入重试返回同一 run；同键不同输入返回 409 |
| GET /v1/apps/{app}/runs/{run} | 返回 appId、instanceId、runId、revision、state、stopEvidence、updatedAt。跨应用或不存在返回 404 |
| POST /v1/apps/{app}/runs/{run}/stop | 带 Idempotency-Key；先保存停止意图，再向所属执行器发送取消，返回 202。终态重复停止返回已有终态，避免重复发信号 |
| PATCH /v1/apps/{app}/runs/{run} | 首轮仅接受 isRead 与 expectedRevision；版本冲突返回 409 和当前版本，客户端重新读取 |
| GET /v1/apps/{app}/runs/{run}/events?after={revision} | 本机 WebSocket 升级入口；返回有序增量，含 eventId、runId、revision、kind、state。断线按游标补读，已超出保留范围时要求先 GET 快照再订阅 |

state 建议包含 queued、running、stopRequested、completed、failed、cancelled、unknown。stopEvidence 单独表示 pending、confirmedExited 或 unverified。收到 stop 请求后仍可显示“等待退出”；只有已登记进程身份及回收证据满足条件时显示“已确认退出”。自然完成先于停止请求时保留 completed。探测超时进入未知显示，不覆盖已经持久化的业务终态。

服务以 run 为单位串行提交。命令幂等键、run 修订号与可回放事件要有同一个可恢复提交边界。先提交再通知，订阅端按修订号去重。崩溃恢复若无法确认旧子进程身份，保留 runId 与 unverified，等待核对；禁止自动重发生成。这里的事件只支撑试点运行，后续再扩展为图 41 的统一事件日志。

## 3. 双客户端验收清单（实施后执行）

准备一个带既有 Pi 历史的临时数据副本，记录旧 run 的 SHA-256 与修改时间。桌面和 CLI 指向同一个测试服务。执行器选用可控制回复和退出时点的本机替身，另用隔离真实 Pi 子进程复验退出证据。以下命令为 CLI 的拟议用法。

| 步骤 | 操作 | 必须留存的证据 |
| --- | --- | --- |
| 1 | 启动服务 A，再让服务 B 打开同一根 | B 报占用；A 保持可读，原文件校验值一致 |
| 2 | 桌面发送一次消息，记下 runId；CLI 执行 `agentx run show --app APP --run ID` | 两端的 appId、instanceId、runId 相同；丢弃创建响应再用同一幂等键重试，只有一次执行器启动 |
| 3 | 保留桌面旧快照，服务推进运行，再由桌面切换页面、标记已读、关闭重开 | 服务端 revision 单调增加；旧客户端保存不能倒退状态；桌面重开不把服务中的活跃 run 标为中断 |
| 4 | CLI 执行 `agentx run stop --app APP --run ID`，桌面同时请求停止；替身延迟退出 | 两端先看到请求已受理；实际退出后得到同一确认，终态只提交一次。让自然完成先到达，再发 stop，结果仍为 completed |
| 5 | 断开桌面订阅，CLI 查询；重连后按游标补读，再分别重启服务和两个客户端 | 两端最终 revision 与状态一致，事件不重放成第二次执行；终态、进程证据、审计能追溯到同一 ID |
| 6 | 在停止意图已保存、进程退出证据尚未写入时中断服务，再启动；测试同 PID 不同启动时间 | 明确显示退出未确认；不误杀其他进程，不自动重新生成；客户端离线时不回退为直接写盘 |
| 7 | 用错误令牌、另一个 appId、同幂等键不同输入操作；尝试并发卸载试点应用 | 请求被拒绝，无越界读写或额外执行；旧 run 字节与修改时间逐一匹配。保留命令回执、事件序列及文件差异清单 |

实施顺序：先验证单写者与旧桌面保存边界（步骤 1、3），再连接真实运行、停止与恢复（步骤 2、4–7）。通过后才扩大服务的写入范围。

### 实现与复验

- [服务协调器](../Runtime/agentxd_runs.py)按应用和幂等键确定运行 ID。重复提交相同输入可取回原记录；同键不同输入返回冲突。停止与自然完成竞争时保留已经取得的实际终态。若重启时只找到未结束的旧运行，标记退出未确认，并阻止同一实例自动重发。
- [Pi 子进程执行器](../Runtime/agentxd_pi.py)登记宿主和子进程身份后才写入请求。仅在匹配的子进程确已回收时给出退出确认。[独立 CLI](../Scripts/agentx)支持 run list、run show 和 run stop。试点桌面和 CLI 均通过本机服务工作，桌面按快照轮询。
- 使用 [隔离验收脚本](../Scripts/run-agentx-pi-pilot-acceptance.py) 的 prepare 创建独立根与受控模型上游。用 launch 启动专用调试包和服务，按脚本打印的文本在桌面发送。重启后运行 verify，脚本核对新客户端进程回执和新 CLI 回读。命令格式见脚本帮助。
- [服务命令回归](../Tests/AgentRuntimeTests/test_agentxd_runs.py)与[进程回归](../Tests/AgentRuntimeTests/test_agentxd_pi.py)覆盖重复创建、重复停止、自然完成后停止、重启恢复、未确认退出和进程回收。WebSocket 事件补读与云端网关属于后续阶段。

### 验收期间的默认数据根访问

一次系统额外拉起的临时客户端未继承隔离环境变量，占用了试点单实例锁。已按进程路径核实并关闭。15:09:17 至 15:13，在安装验收清单覆盖的七个目录中，默认 AgentXManager 根有 17 个文件的修改时间落在该窗口，包含 9 个配置文件和 8 个旅行文件。其余六个根未发现该窗口内的文件修改时间。15:10:39 的正式旅行日志记录一条准备出行事件，本地 Codex 诊断同秒记录一次成功生成。诊断没有调用者 PID 或账单信息。

对比可用的 11 月 9 日 19:39 清单，9 个配置文件中 7 个内容摘要相同、2 个不同，8 个旅行文件摘要不同。该基线早于本次验收三天，不能把全部差异归于额外启动的进程。正式 Pi 历史的 SHA-256 和修改时间均与该基线相同。未回滚正式文件。

隔离启动器已将根路径写入临时包的 LaunchServices 环境。专用包还会在创建桌面客户端前校验数据根、宿主目录和试点标记。实测缺少隔离环境变量时以状态码 78 退出。启动器确认临时进程持有单实例锁、服务可读后才报告就绪；上述最终双端回读使用了修正后的调试包。

## 8. 协作环境与事件补读

使用 Python 3.11 以上版本，在虚拟环境中执行 `python -m pip install -r Runtime/requirements.txt`。WebSocket 使用固定版本 websockets 15.0.1。通过仓库包装器构建桌面调试客户端，再使用第 5、7 节的隔离脚本。

事件与运行状态写入同一个 JSON 文件，每条运行保留最近 64 个修订。GET events?after=revision 支持认证 HTTP 回读和 WebSocket 升级。超出保留范围或游标领先于服务时返回 snapshot_required。既有历史没有事件时，先取得运行快照并从其修订号继续。桌面轮询发现版本变化后补读缺失事件，补读不可用时使用本次取得的服务快照。

2026-11-14 的隔离原生组合验收中，桌面保持同一进程，连接中断期间 CLI 停止真实 Pi，随后 agentxd 作为独立进程退出并重新启动。桌面从游标 2 逐条解码修订号 3、4，事件 ID 与 CLI 一致，窗口显示已确认退出。受控本机模型只收到一次请求，七个正式数据根的前后清单逐字节一致。原生回执和清单保存在本地验收目录。
